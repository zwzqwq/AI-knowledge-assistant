# RAG 进阶：混合检索 + 重排序 —— 架构

> 功能目标：**丰富检索，优化检索知识库结果**。
> 从单路向量检索（similarity/mmr）升级为两阶段混合检索（宽召回 + 精排），让喂给 LLM 的上下文既全又准。
> 原理详解见 `Notes/LangChain/02-RAG进阶-混合检索与重排序.md`，本页只讲"代码怎么组织的、文件怎么分工"。
>
> ✅ 状态：全部落地完成（2026-08-11）。冒烟测试另发现并修复了向量库 96% 重复切片的数据质量问题（见文末附录）。

## 一、改造前后对比

### 改造前（单路）

```
query
  │
  ▼
retriever.get_retriever(search_type)  ← 单路向量检索
  │
  ▼
top-3 直接喂 LLM
```

### 改造后（两阶段混合）

```
query
  │
  ├─ ① 向量检索（看语义）→ top-10    语义路
  ├─ ② BM25（认死理）    → top-10    字面匹配路
  │
  ▼
  合并候选池（去重，约 10~19 篇）
  │
  ▼
  ③ Rerank（小模型打分重排）→ 截断 top-3
  │
  ▼
  top-3 精准文档 → LLM
```

## 二、文件职责（按实现顺序）

| 编号 | 文件 | 职责 | 一句话 |
|------|------|------|--------|
| 01 | `src/rag/bm25_retriever.py` | BM25 召回器 | "认死理"路：分词 → 建索引 → 按 query 检索 top-N |
| 02 | `src/rag/reranker.py` | 精排器 | "评委"：对候选池逐对打分 → 排序 → 截断 top-k |
| 03 | `src/rag/ensemble.py` | 混合编排 | `HybridRetriever(BaseRetriever)`：并行召回 → 去重合并 → 交给 Reranker |
| 04 | `src/rag/retriever.py` | 向量库管理 + 入口 | 新增 `get_hybrid_retriever()` 组装三件套；`get_retriever()` 保留纯向量；入库加去重 |
| 05 | `src/config.py` | 全局参数 | 所有可调参数集中管理 |

## 三、数据流（谁调用谁）

```
retrieve_node (src/agent/nodes.py)
  │  调 retriever.invoke(query)  ← 对外接口不变
  ▼
Retriever.get_hybrid_retriever()   [04]
  │  组装：向量检索器 + BM25Retriever + Reranker
  ▼
Ensemble.invoke(query)             [03]
  ├─ vector_retriever.invoke(query) → top-N   语义路
  ├─ bm25_retriever.invoke(query)   → top-N   认死理路
  │
  ▼
  合并候选池（按内容去重）
  │
  ▼
Reranker.rerank(query, 候选池)      [02]
  │
  ▼
  top-k 精准 Document → generate_node
```

**接口稳定原则**：`retrieve_node` 仍调 `retriever.invoke(query)` 返回 `list[Document]`，下游 `generate_node` **零改动**。换检索策略，接口契约不变。

## 四、关键设计决策

1. **两阶段 = 召回求全 + 精排求准**：召回 N=10 > 精排 k=3，Rerank 才有足够候选"矬子里拔将军"
2. **分数不可比 → Rerank 统一裁决**：向量分（~0-1）和 BM25 分（几十）量纲不同不能直接相加，cross-encoder 重新打分天然统一量纲
3. **BM25 索引 = 全局统计**：IDF 依赖全文档集，全量重建保证分数口径一致（小项目毫秒级够用）
4. **本地缓存 + ModelScope**：embedding/rerank 模型都走"本地缓存优先 → 魔搭下载兜底"，国内环境必做
5. **懒加载单例**：模型只在首次调用时加载一次，避免重复加载 600MB

## 五、依赖清单

| 依赖 | 用途 | 为什么选它 |
|------|------|-----------|
| `rank-bm25` | BM25 算法 | BM25Okapi 三行建索引，成熟实现 |
| `jieba` | 中文分词 | BM25 是词级算法，中文必须分词 |
| `sentence-transformers` | CrossEncoder 加载 rerank 模型 | 项目已装，零额外大依赖 |
| `modelscope` | 国内模型下载 | HuggingFace 国内下不动 |

Rerank 模型加载失败 → 退化为"向量 + BM25 分数简单融合"（归一化后加权相加），保证主链路不挂。

## 附录：冒烟测试发现并修复的数据质量问题（2026-08-11）

**现象**：冒烟测试发现混合检索候选池塌缩——向量 10 条 + BM25 10 条，去重后只剩 3~6 条，Rerank 无料可挑。

**诊断链**：
1. 向量路 top-10 内部只有 2 个唯一文本（6 份复制 + 4 份复制）→ 不是管道 bug
2. 全库统计：422 篇切片只有 **51 个唯一文本，96% 是重复**；最夸张一个文本被存 55 份（55 个不同 chunk id）
3. 根因：**重复入库**——同一批文档被多次上传/导入，每次 `add()` 都追加新副本，无去重
4. 源文件不可恢复（当初 UI 上传的临时文件已清理）→ 库里 51 篇唯一文本是唯一底稿

**修复（A+B）**：
- **A. 原地去重**：`scripts/deduplicate_store.py`（dry-run 预览 + `--execute` 执行 + 删除后自动验证），422 → 51，唯一文本集合一字未变
- **B. 入库防重**：`Retriever.create()/add()` 新增 `_unique_chunks()` 内容去重，`add()` 跳过库中已存在的切片，防止事故重演

**教训（面试可讲）**：检索效果差，先查数据质量再查算法。向量检索对重复数据极其敏感——重复切片让 top-k 被同内容占满，召回多样性塌缩，任何精排算法都救不回来。**脏数据 → 检索系统最隐蔽的性能杀手。**
